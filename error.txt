Assuming you are using AWS Load Balancer Controller with Gateway API in EKS, the architecture is:

                    AWS
┌─────────────────────────────────────────────┐
│                                             │
│  Route 53                                    │
│      │                                      │
│      ▼                                      │
│  ALB / AWS Load Balancer                    │
│      │                                      │
│      │ HTTPS :443                           │
│      │ ACM Certificate                      │
│      ▼                                      │
└──────┼──────────────────────────────────────┘
       │
       ▼
   EKS Gateway
       │
       ▼
   HTTPRoute
       │
       ▼
   Kubernetes Service
       │
       ▼
      Pods
1. ACM certificate
You still create the certificate exactly the same way:

AWS Console → Certificate Manager → Request

Choose:

Public certificate
Domain:

app.example.com
Use:

DNS validation
After validation:

Status = Issued
The important thing is the certificate ARN, for example:

arn:aws:acm:ap-south-1:123456789012:certificate/xxxxxxxx
For an ALB in ap-south-1, the ACM certificate should normally be in ap-south-1.

2. Gateway API is different from Ingress
With Gateway API, you don't put the certificate annotation directly on an Ingress.

You generally have these resources:

GatewayClass
     ↓
Gateway
     ↓
HTTPRoute
     ↓
Service
     ↓
Pod
The Gateway is where you configure the listener and TLS.

For example:

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
spec:
  gatewayClassName: alb
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: app.example.com
      tls:
        mode: Terminate
        certificateRefs:
          - name: my-certificate
      allowedRoutes:
        namespaces:
          from: Same
But there is an important AWS-specific issue here:

ACM certificates are AWS resources, while certificateRefs in Gateway API normally refer to Kubernetes resources.

So you need the AWS Load Balancer Controller's Gateway API implementation to map your configuration appropriately.

3. How does the ACM certificate get connected?
This is the part that usually confuses people.

Your certificate exists in AWS:

ACM
 └── Certificate
      └── ARN
Your Gateway exists in Kubernetes:

EKS
 └── Gateway
      └── HTTPS listener
The AWS Load Balancer Controller watches the Gateway and creates/configures the AWS load balancer.

Conceptually:

Kubernetes Gateway
       │
       │ watched by
       ▼
AWS Load Balancer Controller
       │
       ▼
AWS ALB
       │
       └── ACM Certificate
So you don't put the certificate inside the Pod.

4. Your actual setup
You likely have something similar to:

GatewayClass
    |
    v
Gateway
    |
    +---- HTTPRoute
    |       |
    |       v
    |    Service
    |       |
    |       v
    |      Pods
    |
    +---- HTTPS listener
              |
              v
        ACM Certificate
For example:

Gateway
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: app-gateway
spec:
  gatewayClassName: alb

  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: app.example.com
      tls:
        mode: Terminate
        certificateRefs:
          - name: app-cert
HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: app-route
spec:
  parentRefs:
    - name: app-gateway

  hostnames:
    - app.example.com

  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /

      backendRefs:
        - name: my-service
          port: 80
Then:

https://app.example.com
        ↓
      Route53
        ↓
       ALB
        ↓
 HTTPS terminated using ACM
        ↓
      Gateway
        ↓
    HTTPRoute
        ↓
    Service :80
        ↓
       Pods

Don't blindly create the certificateRefs above yet.

The exact certificate configuration depends on which Gateway API implementation/controller you are running. For AWS, this matters because ACM is not a Kubernetes TLS Secret.

No. You don't need to create Route 53 before ACM. But you do need control over the DNS for your domain to complete ACM DNS validation.

There are two separate things:

ACM
→ creates/manages the SSL certificate

Route 53
→ manages DNS records for your domain

In your case
If you already own a domain, for example:

example.com
but its DNS is managed somewhere else, such as Cloudflare, GoDaddy, Namecheap, etc., you can:

Go to ACM

Request certificate for:

app.example.com
Select DNS validation

ACM gives you a CNAME record

Add that CNAME at whoever currently manages your DNS

ACM validates it and changes to Issued

You do not have to move DNS to Route 53.

What Route 53 would be useful for
Later, to make:

https://app.example.com
point to your AWS ALB, you need a DNS record such as:

app.example.com
       ↓
ALB
You can create that record in Route 53 or in your existing DNS provider.

So your setup can be:

Your existing DNS provider
          │
          ├── ACM validation CNAME
          │
          └── app.example.com → ALB
                              │
                              ▼
                         EKS Gateway
                              │
                         HTTPRoute
                              │
                            Pods
If you don't even have a domain yet
Then yes, you need to buy/register a domain first. You can use Route 53 for that, or another registrar.

For your EKS Gateway API setup, the simplest AWS-only architecture is:

Route 53
   ↓
ACM
   ↓
ALB
   ↓
Gateway API
   ↓
HTTPRoute
   ↓
Service
   ↓
Pods
But Route 53 is not a prerequisite for creating the ACM certificate.

Since you don't have a domain yet, I would set it up in this order for your EKS Gateway API + ALB + HTTPS:

1. Buy/register domain
        ↓
2. Route 53 hosted zone
        ↓
3. ACM public certificate
        ↓
4. EKS Gateway API / ALB
        ↓
5. Connect domain → ALB
        ↓
6. Test HTTPS
Step 1 — Register a domain
The easiest AWS-only approach is Route 53.

Go to:

AWS Console → Route 53 → Domains → Registered domains → Register domains

Search for something like:

myapp-example.com
or whatever name you want.

If available, purchase it. When you register a domain through Route 53, AWS automatically creates a hosted zone and configures Route 53 as the DNS service for the domain. 

For learning/testing, you could choose a relatively inexpensive TLD rather than necessarily .com.

Step 2 — Check the Hosted Zone
After registration:

Route 53 → Hosted zones

You should see:

myapp-example.com
Inside it, you'll normally have records such as:

NS
SOA
Don't delete them.

Step 3 — Create the ACM certificate
Now go to:

AWS Console → Certificate Manager (ACM)

Make sure you're in the same AWS Region as your ALB/EKS load balancer.

Click:

Request → Public certificate

For example:

app.myapp-example.com
I would recommend also adding:

*.myapp-example.com
if you'll have multiple subdomains later.

Choose:

DNS validation

Then request the certificate.

Step 4 — Validate the ACM certificate
Because Route 53 is now your DNS provider, ACM can create the validation CNAME for you.

Open the certificate → Domain validation → Create records in Route 53.

AWS creates the required DNS record, and the certificate should eventually become:

Issued
AWS notes that DNS validation can remain pending for a while after creating the record. 

Step 5 — Configure your EKS Gateway
Now your AWS pieces look like:

Route 53
   │
   │ app.myapp-example.com
   ▼
ALB
   │
   │ HTTPS :443
   │
   │ ACM certificate
   ▼
EKS Gateway
   │
   ▼
HTTPRoute
   │
   ▼
Service
   │
   ▼
Pod
The important part here is that your ACM certificate terminates TLS at the AWS load balancer, rather than inside your application pod.

Step 6 — Point your domain to the ALB
Once your Gateway API creates the ALB, you'll have an ALB DNS name similar to:

k8s-xxxxx.ap-south-1.elb.amazonaws.com
Then create a Route 53 record:

app.myapp-example.com
        ↓
ALIAS
        ↓
Your ALB
So when someone opens:

https://app.myapp-example.com
the request goes:

Browser
   ↓ HTTPS
app.myapp-example.com
   ↓
Route 53
   ↓
ALB
   ↓
ACM certificate
   ↓
Gateway API
   ↓
HTTPRoute
   ↓
Service
   ↓
Pod
